一个做传感器与云端之间边缘网关的开源平台，采、存、转、缓冲一条龙

写在前面

接工厂数据采集的活儿，真正吃时间的往往不是上层业务，是底下那摊设备接入和数据管道。PLC 协议五花八门、车间网络时断时续、数据要同时喂给 MES 和云端——这些脏活，Fledge 帮你兜住了。

它先解决你的痛点

做 OT 边缘采集，下面这些麻烦你多半都碰过。

1.协议对不上。现场 Modbus RTU、OPC UA、自定义串口混着来，每种都得单独写适配。

2.断网就丢数据。车间网络一抖，采到的点全没了，补都补不回来。

3.一份数据要喂多个下游。MES 要一份、云端分析要一份、本地 historian 还要一份。

4.上行带宽贵。原始高频数据全往上送，带宽和存储都扛不住。

5.边缘预处理缺工具。想在上传前做 RMS / FFT，得自己另搭一套。

6.平台太重跑不动。有些边缘节点就是个树莓派，重微服务框架直接趴窝。

7.设备到货前没法验证。采集逻辑写好了，没设备联调不了。

核心能力

Fledge 的定位很清晰：做传感器 / PLC 设备与云端之间的边缘网关，采、存、转一条龙。

南向插件把设备数据采集进来

South 插件覆盖 Modbus、OPC UA、MQTT、SenseHAT 等多种协议和传感器，新接一种设备基本是装插件、填参数的事。

South Services（南向数据源服务）列表页，以表格展示所有已配置的数据采集服务。每行含服务名（如 SenseHAT）、运行状态（绿色 enabled 标签）、所用插件及版本（sensehat 1.7.0）、提供的资产列表（pressure / temperature / humidity 等）与累计读数；右上角「Add +」用于新增南向数据源。

内置缓冲区，断网不丢点

采集到的数据先落本地 SQLite / PostgreSQL，网络断开时缓在那儿，恢复后自动续传——这是 Fledge 最核心的工业级能力。

北向插件把数据转发出去

North 插件支持 PI System（OMF）、REST、MQTT 等多种目标，同一份数据能同时转发给多个 historian / 云服务。

North Instances（北向转发服务）列表页，展示所有已配置的数据发送目标。表格列含进程名（如 Plant Librarian）、状态（enabled）、插件类型、版本与已发送量（Sent）；右上角「Create North Instance +」用于新建转发任务。Fledge 可同时向多个目标（PI System、OMF、REST 等）转发同一份数据。

Dashboard 一眼看全局

实例名、接收 / 发送量、运行时间、各资产读数曲线都在一屏里，运维不用再拼命令。

Fledge Dashboard 主界面：左侧功能导航（Dashboard、Assets、South、North、Notifications 等），右侧上方显示实例名、已接收 / 已发送量与运行时间，主区域以折线图呈现「Readings received by Fledge」全局趋势与单个资产（如 sensehat/temperature）的读数曲线，右上角可切换时间窗口。

资产数据图形化查看与预处理

每个资产都能拉出折线图看趋势，配合 Filter Pipeline 还能在上行前做计算，少送无用数据。

资产数据图形化查看页，以车床 lathe1014 为例：顶部为资产名、时间范围（10 minutes）与资产选择下拉；提供 Graph / Tabular Data / Summary 三个标签页。Graph 视图用不同颜色折线展示多个数据点（depth 深蓝、rpm 橙、x 绿），右侧带播放 / 暂停 / 步进等时间导航控件，可看出转速的周期性波动。

它的优势在哪里

和几个常见平台比，Fledge 的差异化很明确：专注 OT 边缘、重缓冲、轻量可上树莓派。

与同类平台的差异

vs Node-RED：Node-RED 是通用流程编排（JS 节点流），上手快但工业感弱；Fledge 专注 OT 采集，缓冲和 South/North 分离更专业。

vs ThingsBoard：ThingsBoard 是全栈云端平台；Fledge 纯边缘聚焦，常互补：Fledge 在边缘采数，ThingsBoard 在云端展示。

vs Apache EdgeX：EdgeX 微服务 / Docker 重型架构，最低要 1GB RAM；Fledge 更轻，树莓派 4 就能跑，GUI 开箱即用。

vs Mainflux：Mainflux 云原生、API 驱动，灵活但要自己集成；Fledge 预打包插件，「装上就能用」门槛更低。

⚠️ 性能上：Fledge 的 C/C++ 核心很省资源，树莓派 4（2GB）即可跑完整实例，内存通常几百 MB，远低于 EdgeX 的 1GB 起步。生产环境把默认 SQLite 换成 PostgreSQL 更稳。

使用场景

下面几类工业场景用得最多。

•工厂数据采集监控：从 PLC、数控机床、传感器采实时数据，经 Modbus / OPC UA 接入后缓冲转发到 PI / MES。

•协议转换与归一化：现场协议五花八门，South 插件统一转成标准资产 / 读数模型。

•断网缓冲续传：车间网络不稳或计划维护时，数据缓在本地，恢复后自动补传，不丢点。

•边缘预处理：上行前用 Filter Pipeline 做 RMS / FFT / 去重，省带宽省存储。

•多目标分发：同一条产线数据同时转发到 PI System、云端分析与本地库。

•预测性维护：采振动 / 温度做边缘 RMS/FFT，异常触发通知告警。

•树莓派边缘节点：在 ARM 边缘设备上跑完整 Fledge，适合分布式小产线。

✅推荐 工业边缘 / 小产线：树莓派 4（2GB）能跑，内存几百 MB，上手约 1 小时，Apache-2.0 可闭源商用、可白标。

⚠️要掂量 超高频采集（数千点 / 秒）默认 SQLite 会成瓶颈，上生产建议切 PostgreSQL。

❌别硬上 想在 Windows / macOS 上开发（仅 Linux）；或想拖拽搭可视化大屏（它不是 Grafana，展示能力有限）。

快速上手

技术栈就这几样，点评一下。

技术栈点评

C/C++ + Python：性能关键路径用 C/C++，插件 / 脚本用 Python，分工清晰。

SQLite / PostgreSQL：默认 SQLite 轻量；生产用 PostgreSQL 更扛造。

Make + CMake：构建系统老牌但稳，requirements.sh 一把装好依赖。

Linux only：只支持 Ubuntu / Raspbian 等 Linux，开发机得是 Linux 或 WSL2。

⚠️ 默认账号 admin / fledge 是硬编码密码，文档明确要求立即改；生产环境忘了改是大坑。

踩过的坑

几个容易栽的地方。

⚠️ 只支持 Linux，开发测试必须 Linux 环境（虚拟机 / WSL2 / 树莓派都行）。

⚠️ Docker 镜像不在 Docker Hub，在私有仓库，拉取需配 insecure registry；且目前只提供 Ubuntu 20.04 版本。

⚠️ 资产名必须全局唯一，多个传感器共用插件时容易重名导致数据覆盖；GUI 不是大屏构建器，展示能力有限。

开源协议与合规边界

这一节把协议讲清楚，方便你判断能不能接私活、能不能交付。

协议与你能不能这么干

协议是什么：Apache-2.0。盘点表标的是 Apache 2.0，仓库 LICENSE 实际也是 Apache-2.0，两者一致。

能不能二次开发：✅ 能。fork 改、加功能、自己编译都行，不用开源你的改动。

能不能自用 / 接私活 / 交付客户：✅ 能。可闭源商用、可塞进给客户的项目里卖，只要保留 NOTICE 声明。

要不要署名 / 保留声明：要保留原作者的版权与 NOTICE 声明；改了代码不强制开源。

商标 / 商用边界：不能去掉对方 Logo 当自己产品，也不能拿作者名背书、号称自研。

⚠️ 一句话：Apache-2.0 是最省心的那类——闭源商用、白标、接私活都行，保留 NOTICE 即可。所以这篇标题我才敢写「免费」。
